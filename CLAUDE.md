# terraform-provider-duploai

Terraform provider for DuploCloud/DuploAI. Built on `terraform-plugin-framework` (not SDKv2). Registry: [registry.terraform.io/providers/duplocloud/duploai](https://registry.terraform.io/providers/duplocloud/duploai)

## Key architectural insight

**Adding a resource requires no Go code — only a JSON spec file.**

Each `duplocloud/specs/<name>.json` file is embedded at build time and registers one `duploai_<name>` resource. A single generic engine (`dynamic_resource.go`) handles all CRUD for every resource.

```
main.go → duplocloud/provider.go → duplocloud/specs/*.json
                                 → duplocloud/dynamic_resource.go
                                 → duplosdk/rest_resource.go → DuploAI API
```

- `duplocloud/` — provider, dynamic engine, type system, validators, specs
- `duplosdk/` — REST client, endpoint abstraction, async waiter
- `examples/` — `.tf` + `import.sh` per resource (required by CI)
- `docs/` — auto-generated, do not edit manually (`make doc` regenerates)
- `docs-internal/` — [architecture](docs-internal/architecture.md), [spec reference](docs-internal/spec.md), [git hygiene](docs-internal/git-hygiene.md), [release process](docs-internal/release-process.md)

## Adding a resource

Before starting: read an existing similar spec in `duplocloud/specs/` and follow its pattern.

1. Create `duplocloud/specs/<name>.json` — see [docs-internal/spec.md](docs-internal/spec.md) for the full spec reference
2. Add `examples/resources/duploai_<name>/resource.tf` and `import.sh`
3. Add `examples/data-sources/duploai_<name>/data-source.tf`
4. Run `make doc && make vet && make build && make test`
5. Verify with `terraform validate` and `terraform plan` against a real host

## Generated files — do not edit manually

`docs/**` is fully auto-generated by `tfplugindocs`. Always regenerate with `make doc` after changing specs or examples. Never edit these files directly.

## Debugging resource issues

Most problems originate in the spec JSON, not the Go engine. The engine is shared across all resources and rarely needs changes. When a resource misbehaves, check in this order:

1. `apiPath` mappings — is the field going to/from the right JSON path?
2. URL path parameters — does every `{placeholder}` in `uriBase` have a matching attribute with no `apiPath`?
3. `waiter` config — is `deprovisionedState` set when `deprovision` is used?
4. `computed`/`optional`/`required` flags — see the gotchas table below
5. Request body structure — use `duplo_host` logs or API docs to compare actual vs expected payload

## Non-obvious spec gotchas

| Mistake | Symptom | Fix |
|---|---|---|
| `default` without `computed: true` | Provider panics at startup | Add `"computed": true` |
| `deprovision: {}` without `deprovisionedState` in waiter | Delete hangs until timeout | Add `"deprovisionedState": "DeProvisioned"` |
| `required + computed` on same attribute | Framework panics at schema build | Use `optional + computed` instead |
| Body field with no `apiPath` | Silently treated as URL path param, not sent in body | Add `"apiPath": "<field>"` |
| Async resource with no `waiter` | `apply` returns before resource is ready | Add `"waiter": {}` minimum |

## Git workflow

- **All PRs target `develop`** — `master` is CI/CD-only
- **Branch naming:** `DUPLOAI-XXXX-short-description`
- **PR title:** 20–72 chars, no ClickUp ID (goes in body, not title)
- Full rules and release flow: [docs-internal/git-hygiene.md](docs-internal/git-hygiene.md)
